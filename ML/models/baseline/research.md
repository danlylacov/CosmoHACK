# Baseline: прогноз космической погоды для планирования ВКД

Статус: согласованная концепция и план проверки. Модель, вероятности и правила решения ниже ещё предстоит реализовать и проверить на данных.

## 1. Результат модели

Один запуск выдаёт **64 последовательных окна по 30 минут на следующие 32 часа**. Каждое окно содержит прогноз физических показателей, неопределённость, вероятность неблагоприятных условий и флаг допустимости ВКД по правилам прототипа.

Для момента прогноза `t0` на получасовой сетке UTC:

```text
window[h] = [t0 + h × 30 минут, t0 + (h + 1) × 30 минут), h = 0…63
```

Горизонт покрывает поиск начала работ в пределах 24 часов и ВКД длительностью до 8 часов. Даже при нехватке данных сохраняются все 64 строки: неизвестные значения и решения обозначаются `null` с причиной.

Основная цепочка: **прогноз показателей → вероятность превышения порогов → флаг ВКД**.

## 2. Входные данные: актуальный контракт CSV

### Измерения — `series.csv`

`time_utc` обозначает начало окна `[time_utc, time_utc + 30 минут)`. Для частых измерений текущий [конвертер](../../space_weather_model_data/series_to_csv.py) формирует:

| Колонка | Значение | Использование в модели |
|---|---|---|
| `<metric>` | Среднее за окно; суффикса `_mean` нет | Уровень потока, прогноз среднего и накопленного потока |
| `<metric>_min` | Минимальное непустое значение | Нижний уровень и размах колебаний |
| `<metric>_max` | Максимальное непустое значение | Пики и разметка превышений порогов |
| `<metric>_last` | Последнее непустое значение по времени | Состояние к концу окна и направление изменения |
| `<metric>_count` | Число непустых конечных значений после удаления дублей внутри ряда | Признак обеспеченности измерениями |

Эти дополнительные колонки создаются для измерений с интервалом меньше 30 минут, включая отдельные точки без указанного интервала. Для интервалов от 30 минут они не создаются. Kp/ap и другие длинные интервалы повторяются в пересекающихся окнах; такое повторение не добавляет независимых измерений.

В пустом окне `_count = 0`, остальные статистики пустые. Пропуск не заменяется нулём. При объединении рядов среднее рассчитывается сначала внутри каждого ряда, затем между рядами с равными весами. Минимум, максимум и количество учитывают все их частые точки; одновременные последние значения усредняются.

**Полнота сейчас представлена количеством точек, а не готовой долей покрытия.** Для выбранного регулярного источника можно дополнительно вычислить `coverage_fraction = observed_slots / expected_slots`: число временных позиций с пригодными измерениями относительно ожидаемого числа. Например, при пятиминутной частоте в полном получасовом окне ожидаются 6 позиций. Суммарный `_count` разных источников нельзя просто делить на 6: совпадающие измерения могут увеличить число записей без улучшения покрытия. Без частоты, происхождения и времён исходных точек точное покрытие неизвестно.

Единицы, источники, версии и флаги качества берём из сохранённого `result.json`. Конвертер не исключает все числовые значения с плохими флагами качества. Для обучения и разметки нужна зафиксированная политика выбора источника и качества; при необходимости статистики пересчитываются из исходных пригодных точек. Сам CSV не подтверждает качество измерений.

### Выпущенные прогнозы — `forecasts.csv`

Нерегулярный ряд: `issued_at_utc` и текстовые продукты `discussion`, `3day_forecast`, `reports_solar_geophysical_activity`. Из текста извлекаются только явно указанные вероятности, уровни, периоды действия и ожидаемая динамика; сохраняются ссылка на исходный выпуск и результат разбора.

Для запуска выбираются выпуски, доступные к моменту отсечения. Их информация применяется только к соответствующему периоду действия. Суточная вероятность остаётся признаком суточного горизонта: её нельзя копировать в 48 окон и называть получасовой вероятностью. Разные версии в одной CSV-ячейке требуют проверки по исходникам.

## 3. Что прогнозируем

Приоритетные ряды — `proton_flux_above_10_mev`, `proton_flux_above_50_mev`, `proton_flux_above_100_mev`. Для каждого будущего окна прогнозируем **среднее и максимум**; минимумы, последние значения и количество исходных точек используем как входные признаки. Дополняем их лагами, изменениями и размахом за прошлые 1, 3, 6 и 24 часа, с масками пропусков и давностью данных.

Рентгеновский поток и выпуски NOAA могут дать информацию о развитии событий. Kp/Hp30, солнечный ветер и Bz описывают геомагнитный контекст. Пользу каждой группы признаков проверяем сравнением моделей; коррелирующие сигналы не суммируются как независимые угрозы. События DONKI и спектры находятся вне этих двух CSV и потребуют отдельной подготовки, если будут включены.

Для первого исследования задаём событие `adverse[h]`:

```text
max(J_≥10 МэВ внутри window[h]) ≥ 10 pfu
ИЛИ
max(J_≥100 МэВ внутри window[h]) ≥ 1 pfu
```

Это пороги предупреждений [NOAA GOES Proton Flux](https://www.spaceweather.gov/products/goes-proton-flux), где `1 pfu = 1 протон/(см²·с·ср)`. Они задают проверяемую цель по внешней среде и не являются нормативами допуска космонавта. Операционное определение события NOAA и наш признак превышения внутри получасового окна различаются.

`p_adverse[h]` — вероятность хотя бы одного такого превышения внутри окна. Её обучаем и калибруем по совместной целевой метке, без сложения вероятностей по энергетическим каналам. Валидное наблюдаемое превышение даёт метку `1`; метка `0` требует достаточного покрытия обоих каналов без превышений. Иначе метка неизвестна и не участвует в обучении как отрицательная.

Поток на GOES служит показателем внешней обстановки. Для перехода к дозе на МКС нужны траектория, геомагнитная защита и свойства скафандра; такой расчёт в эту модель пока не входит. Эти зависимости описывает [NASA SRAG](https://srag.jsc.nasa.gov/spaceradiation/how/how.cfm).

## 4. Выходной контракт

Метаданные запуска: `forecast_origin_utc`, `issued_at_utc`, `data_cutoff_utc`, `model_version`, `policy_version`, версии/хеши входных данных, единицы, уровень интервалов неопределённости и `assessment_scope = space_weather_proxy`. Момент отсечения не позже начала прогнозного горизонта.

| Поле строки | Содержание |
|---|---|
| `start_utc`, `end_utc` | Границы получасового окна |
| `<metric>_mean_pred`, `<metric>_max_pred` | Прогноз среднего и максимума выбранного показателя |
| `<metric>_mean_lower`, `<metric>_mean_upper` | Интервал неопределённости среднего |
| `<metric>_max_lower`, `<metric>_max_upper` | Интервал неопределённости максимума |
| `p_adverse` | Калиброванная вероятность заданного неблагоприятного события, либо `null` |
| `eva_allowed` | `true`, `false` или `null` по правилам прототипа |
| `reason` | Факторы, пороги и причины решения или невозможности оценки |
| `source_refs` | Ссылки на использованные измерения и выпуски прогнозов |

В JSON числовые прогнозы можно группировать по показателям; в CSV они раскладываются в отдельные колонки. Интервалы описывают неопределённость будущих значений, а наблюдаемые `_min`/`_max` — фактический размах прошлого окна. При отсутствии проверенной оценки неопределённости границы и вероятность остаются `null`.

## 5. Baseline и проверяемое развитие

1. **Простая база для сравнения:** последнее завершённое пригодное окно. Его среднее и максимум повторяются на все 64 будущих окна; сохраняются давность и полнота исходных данных. Это прогноз сохранения текущего состояния. Он не даёт обоснованных числовых вероятностей сам по себе.
2. **Обучаемый baseline:** табличная модель по прошлым агрегатам и доступным выпускам прогнозов. Для каждого горизонта она оценивает среднее, максимум и событие превышения. Все 64 оценки строятся из одного среза доступных данных; фактические будущие значения во входы не подставляются.
3. **Вероятности и интервалы:** калибруются на отдельном временном периоде. Проверка проводится отдельно для ближнего и дальнего горизонта, включая 24–32 часа. До проверки конкретного горизонта решения по нему могут оставаться `null` с причиной `unvalidated_horizon`.

Для протонных прогнозов проверяем неотрицательность, согласованность среднего и максимума, порядок границ интервалов. Выбор обучаемого алгоритма и параметров делается по результатам сравнения; улучшение качества заранее не предполагается.

## 6. Флаг ВКД и выбор времени работ

`eva_allowed` относится к нахождению снаружи **в указанные 30 минут и в пределах оцениваемого механизма**. Это рекомендация исследовательского прототипа по внешней обстановке, а не эксплуатационный допуск.

Правила хранятся в отдельной версионируемой конфигурации:

- `true`: данных достаточно, горизонт проверен, прогноз удовлетворяет выбранной политике допустимости;
- `false`: достаточно оснований считать окно неблагоприятным по этой политике;
- `null`: критические пропуски, устаревание, непроверенный горизонт или неопределённость, не позволяющая выбрать решение.

Для вероятностной модели политика задаёт пороги принятия решения и требования к качеству/калибровке. Для детерминированной базы возможна отдельная политика по прогнозируемым значениям без выдуманной вероятности. Порог решения не выбирается автоматически равным `0.5`; его обосновываем соотношением пропусков событий и ложных предупреждений.

Шестичасовая ВКД при старте на границе сетки занимает 12 окон. Для рекомендации по всему выходу нужны допустимые оценки всех пересекаемых окон. При произвольном старте учитываем и частично пересекаемые окна. Наличие неблагоприятного окна даёт неблагоприятную рекомендацию по этой политике; при отсутствии таких окон, но наличии неизвестных, итог остаётся неизвестным. Вероятности по соседним окнам не перемножаем: они зависимы.

Сравниваем варианты одинаковой длительности по пиковому потоку, пересечению с неблагоприятными окнами, полноте оценки и интегралу прогнозируемого среднего потока по времени. Последний имеет единицы `протоны/(см²·ср)` и служит прокси накопленного потока в месте внешнего измерения, не дозой человека. Получасовой максимум не определяет точную длительность превышения внутри окна. Сокращение ВКД рассматривается как отдельное изменение плана.

## 7. Временная честность

- Агрегат окна доступен после его завершения и получения данных. Открытое последнее окно не используется как полное.
- Время измерения, время публикации, срок действия прогноза и время загрузки различаются. Входы каждого исторического запуска фиксируются на `data_cutoff_utc`.
- Повторённый в CSV итоговый Kp за три часа или суточный индекс нельзя использовать с начала соответствующего интервала: в тот момент итог ещё не известен.
- Архивные исправления, поздние анализы и восстановленные значения не доказывают доступность в прошлом. При неподтверждённой версии/публикации данные пригодны для ретроспективной проверки, но не для строгого прогноза из прошлого.
- Для строгого исторического режима первой опорой служат датированные исходные выпуски NOAA. Наличие только CSV недостаточно для проверки происхождения и доступности каждой версии.

## 8. План проверки

Проверочный период из ТЗ — 1 мая — 30 июня 2024 года. Обучение, настройка и калибровка используют отдельные более ранние данные; при последовательной проверке учитываем доступность данных для каждого запуска. Все 32 часа целевых окон обучающего примера должны закончиться до начала отложенного периода. Случайное перемешивание соседних окон не применяется; одно событие не делится между обучением и тестом.

Сравниваем простой прогноз сохранения состояния, использование только доступного внешнего прогноза и обучаемый baseline на одинаковых срезах информации. Включаем выраженное протонное событие и спокойный контрольный период; даты подтверждаем исходными наблюдениями. Указываем число независимых событий, а не только число получасовых строк.

Проверяем ошибку среднего/максимума потока, пропуски и ложные предупреждения, заблаговременность, калибровку `p_adverse` и покрытие интервалов неопределённости. Результаты разбиваем по горизонтам до 6, 6–12, 12–24 и 24–32 часов. Отдельно учитываем долю `null` и качество сравнения целых окон ВКД. При редких событиях не заявляем надёжную вероятность без достаточной проверки.

## 9. Связь с полной задачей

Это одна линия анализа — космическая погода. [ТЗ](../../Постановка_задачи_—_Прогнозирование_рисков_ВКД.pdf) требует также второй самостоятельный механизм и содержательное использование траектории МКС. Возможное дополнение — освещённость вдоль орбиты с явно заданным ограничением конкретных работ. Несколько протонных каналов не заменяют разные механизмы.

Контракт поддерживает проверяемость, временное отсечение и сравнение окон из [критериев оценки](../../Критерии_оценки_—_Прогнозирование_рисков_ВКД.pdf). Общий вывод сервиса о ВКД должен учитывать все выбранные механизмы; благоприятная космическая погода не закрывает неизвестность по другим факторам.
